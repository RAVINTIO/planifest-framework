## Findings (severity-ordered)

- [major] `requirements/req-007-story-split-step.md` "Where the step lives" and "The split step": the loop runner copy of the step runs inside a fix loop. A yes answer moves each criterion with its concern to a new requirement file and splits the brief's story. `ratchet-check.mjs:86-104` guards every `- [ ]` line under `## Acceptance Criteria` in any `plan/current/*.md` file. `ratchet-check.mjs:238-248` compares one file at a time, so a moved criterion counts as removed and the write exits 2. Only a human-written `.ratchet-approve` line lets it through, and agents must never write that marker. In `autonomous` no human is present, so the yes branch can't complete. The new critic rubric row then fails the requirement on every iteration. Fix: state how a split works while a loop is active. One option keeps the existing criteria in place and puts only the new concern's criteria in the new file. Another escalates the split to the human on the loop for a ratchet approval. Add a suite case or a note that names the chosen route.
- [minor] `requirements/req-007-story-split-step.md` "The split step": a keep answer is recorded as "a one-line reason", but the requirement doesn't say where. The design critic runs in a fresh context and sees only artifacts, so its new rubric row can't find the answer. Name the place, such as a line in the requirement file or the phase build-log block.
